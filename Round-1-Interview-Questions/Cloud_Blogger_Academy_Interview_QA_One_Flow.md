## 11. What is a configuration conflict?
**Answer:**

“A configuration conflict occurs when different environments, applications, services, or components have incompatible or inconsistent configurations.

For example, an application may work in development because it uses one version of a library or environment variable, but fail in production because the configuration is different.

Common examples include different application versions, environment variables, ports, credentials, permissions, networking configurations, or infrastructure settings.

To avoid configuration conflicts, I prefer using **Infrastructure as Code, configuration management, environment-specific variables, version control, and automated CI/CD pipelines**.

The goal is to make environments consistent and deployments repeatable.”

## 13. How would you communicate a production outage to a non-technical stakeholder?
**Answer:**

“I would avoid using technical terminology and focus on the business impact.

For example, instead of saying:

‘The Kubernetes ingress controller is failing because of a networking issue.’

I would say:

‘The application is currently unavailable because we are experiencing an infrastructure-related issue. Our technical team has identified the problem and is working on restoring the service.’

I would provide three important things:

1. **What      is impacted?**
2. **What      is being done to resolve it?**
3. **What      is the expected next update?**

I would also avoid giving an unrealistic ETA. If we don't have a confirmed recovery time, I would clearly communicate that we are investigating and provide the next update at a specific time.”

## 27. How do you handle production issues?

- Verifying application and service status
- Reviewing AKS pod status and container logs
- Checking network connectivity and DNS
- Validating recent deployments or configuration changes
- Checking backup or replication status in DR environments

If the issue is deployment-related, I verify the CI/CD pipeline logs and perform rollback activities if required to restore the stable version.

For AKS-related issues, I check pod events, deployments, ingress, container logs, and scaling conditions to identify failures.

During critical incidents, I coordinate with application teams, network teams, and management while providing regular status updates and ensuring SLA compliance.

Once the issue is resolved, I perform root cause analysis (RCA), document the issue, and implement preventive measures or automation to avoid similar incidents in the future.
